# AI 资讯聚合站 PRD（产品需求文档）

| 项 | 内容 |
| --- | --- |
| 文档版本 | v0.1 |
| 日期 | 2026-11-11 |
| 状态 | 待评审 |
| 关联课题 | 《AI 资讯聚合中的多源事件合并与摘要方法研究及系统实现》 |
| 一句话定义 | 把多个来源里"同一件事"的报道合并成一个事件，每个事件配一句摘要，任何人打开浏览器就能看。 |

---

## 1. 背景与问题

科技、金融、AI 等领域的信息更新节奏快、来源分散。同一件事往往在数小时内被多家媒体重复报道：标题不同、角度不同、正文大面积重叠。

用户面对两类成本：

1. **重复阅读成本**：同一事实被消费多次；
2. **判断成本**：需要自行识别多条内容是否指向同一事件。

现有聚合工具（RSS 阅读器、资讯客户端）只完成"汇聚"，没有完成"归并"，用户仍然要逐条读才能知道哪些是重复的。聚合的价值停留在搬运层面。

本产品要解决的就是归并这一层：**以事件为单位组织信息，而不是以文章为单位。**

## 2. 目标与非目标

### 2.1 目标

| 编号 | 目标 | 衡量方式 |
| --- | --- | --- |
| G1 | 同事件多源报道被正确合并 | 人工标注集上成对 F1 ≥ 0.8 |
| G2 | 用户单次浏览即可掌握当日要点 | 首页一屏内可读完当日事件标题 |
| G3 | 任何人无需注册即可访问阅读 | 公网 URL 直接打开，无登录墙 |
| G4 | 支持多领域并行扩展 | 新增一个主题只需配置，不改代码 |
| G5 | 日常运行成本可控 | LLM 支出 ≤ 5 元/天 |

### 2.2 非目标（明确不做）

以下内容写进论文的"未来工作"，本期不实现：

- **用户系统**：不做注册、登录、权限、多租户。
- **评论与社交**：不做点赞、评论、分享、关注。
- **移动端**：只做桌面 Web，不做响应式布局与移动端适配。
- **个性推荐**：不做"猜你喜欢"，只按时间与主题组织。
- **全文翻译**：英文源保留原文，不做翻译。
- **内容审核**：不做自动审核与人工审核流程。
- **金融深度定制**：金融主题只做通用合并，不做行情、K 线、股票实体对齐。

## 3. 用户与场景

### 3.1 角色

| 角色 | 描述 | 权限 |
| --- | --- | --- |
| 访客（任何人） | 通过公网 URL 打开，浏览、搜索 | 只读 |
| 站主（你） | 维护数据源、触发抓取、调参、看实验 | 读 + 管理操作（凭 Token） |

> **设计说明**：访客不需要任何身份即可阅读，因此"收藏"与"已读"无法存于服务端。这两项状态保存在浏览器本地，换设备不同步。这是为了换取"零注册"的体验，属于有意取舍，不是缺陷。

### 3.2 核心场景

**场景 A（每日浏览）**
早上打开浏览器首页 → 看到"今日事件"时间线，约 20~40 个事件 → 扫标题和一句话摘要 → 点开感兴趣的 → 看到 6 家媒体的报道并排 → 点原文跳转 → 标记已读。

**场景 B（追某个主题）**
顶部切到"综合科技"主题 → 只看该主题事件 → 收藏两条待细看 → 下午回来在收藏列表里继续。

**场景 C（找特定信息）**
搜"英伟达财报" → 命中相关事件与文章 → 按时间排序 → 进入事件详情。

**场景 D（站主维护）**
发现某源失效 → 进管理页停用该源 → 加一个新源 → 手动触发一次抓取 → 看抓取日志。

## 4. 关键产品决策

这一节是评审和答辩时最容易被追问的地方，每条都写清"为什么"。

### 4.1 无账号 + 本地收藏

**决策**：不做用户系统，收藏与已读存 `localStorage`。

**理由**：产品定位是"任何人打开就能看"，加登录会直接摧毁这个体验；而收藏/已读是弱状态，丢失代价低。

**代价**：换设备不同步、清缓存会丢。

**应对**：提供"导出收藏为 JSON"的按钮，成本 20 行代码。

### 4.2 公开只读 + 写操作凭 Token

**决策**：所有页面公开可访问；触发抓取、增删数据源等操作需要 `Admin-Token`。

**理由**：公网暴露的写接口会被扫到。抓取会消耗外部请求与 LLM 费用，不能开放给任何人。

**代价**：自己每次管理要带 Token。

**应对**：Token 存浏览器本地，管理页自动带上，日常无感。

### 4.3 以"主题"而非"领域"建模

**决策**：数据模型引入 `Topic`，源与事件都归属主题；每个主题可独立配置聚类阈值与摘要提示词。

**理由**：你明确要求能扩展到股市、金融、科技。若把领域写死，第二期就得重写。

**代价**：多一层关联，查询稍复杂。

**应对**：MVP 只开 2 个主题（AI、综合科技），但模型支持任意新增。

### 4.4 以"事件"而非"文章"作为组织单位

**决策**：首页展示事件，文章只在事件详情里出现。

**理由**：这是产品的全部价值所在。如果首页还是文章流，就和 RSS 阅读器没有区别。

**代价**：合并算法错了，用户看到的组织就是错的。

**应对**：提供"手动拆分/合并事件"的纠错入口（P1）。

## 6. 功能清单

### 6.1 P0（MVP，必须完成）

| 编号 | 功能 | 说明 | 验收标准 |
| --- | --- | --- | --- |
| F01 | 源管理 | 增删改查数据源，设置所属主题与启用状态 | 后台可添加一个 RSS 源并立即生效 |
| F02 | 定时抓取 | 每日定时 + 手动触发；单个源失败不影响其他源 | 50 个源全量抓取 5 分钟内完成 |
| F03 | 正文抽取 | 从 RSS 摘要或原文页提取正文并清洗 | 抽取成功率 ≥ 90%，无导航栏残留 |
| F04 | 文章级去重 | SimHash 指纹 + 汉明距离判定近似重复 | 重复文章不再进入待聚类队列 |
| F05 | 事件聚类 | 标题+首段向量相似度 + 时间窗，将同事件文章归并 | 同一事件的文章被归入同一事件 |
| F06 | 事件摘要 | 对合并后的多源材料生成一句话摘要 | 摘要不包含原文没有的事实 |
| F07 | 时间线 | 按天分组展示事件，支持分页与主题过滤 | 首屏 1.5 秒内可交互 |
| F08 | 事件详情 | 展示摘要、多源报道列表、相似度分数、原文链接 | 点开一个事件可见 ≥2 家来源并列 |
| F09 | 搜索 | 事件与文章全文检索 | 关键词命中，结果按时间倒序 |
| F10 | 收藏 / 已读 | 本地存储，列表内可筛选"未读" | 刷新后状态保留 |
| F11 | 主题切换 | 顶部切换，URL 可直达 | 切换后列表即时过滤 |
| F12 | 公网部署 | 只读访问 + 管理 Token + 基础限流 | 外网可直接打开，无登录墙 |

## 7. 核心流程

### 7.1 采集与处理（后台，每日定时）

```
cron 触发
  ↓
遍历启用的源 → 拉取 RSS
  ↓
正文抽取（失败则用 RSS 摘要截断）
  ↓
清洗（去 HTML、去广告、压缩空白）
  ↓
文章级去重：SimHash 64 位 → 汉明距离 ≤ 阈值 判为重复
  ↓
事件聚类：同主题 + 24 小时窗口内
          标题与首段向量 → 余弦相似度 → 阈值判定 → 单遍聚类
  ↓
事件摘要：把事件下的多篇正文拼成材料 → LLM 生成一句话摘要
  ↓
写入数据库 → 更新事件计数
  ↓
记录 FetchLog（新增数、去重数、合并数、错误）
```

**幂等要求**：同一篇文章重复抓取不得产生重复记录（以 URL 归一化后的哈希为唯一键）。

### 7.2 浏览与阅读（前台）

```
打开首页 → 请求今日事件（分页）→ 渲染时间线
  ↓
点击事件 → 请求事件详情 → 展示摘要 + 多源并列
  ↓
点击"原文" → 新窗口跳转 → 本地标记已读
  ↓
点击星标 → 写入 localStorage → 列表即时更新
```

### 7.3 搜索

```
输入关键词 → 请求 /search
  ↓
SQLite FTS5 检索（中文先经 jieba 分词写入索引字段）
  ↓
合并事件与文章两类结果 → 按时间倒序 → 高亮关键词
```

> **技术说明**：SQLite 自带 FTS5 不含中文分词，需在写入时用 `jieba` 把标题与正文预分词成空格分隔的字符串，单独存一列供索引使用。

## 8. 数据模型

```
Topic(id, slug, name, description, config_json, created_at)
     config_json: {simhash_threshold, cosine_threshold, time_window_hours, summary_prompt}

Source(id, topic_id, name, feed_url, type, enabled, last_fetch_at, fail_count)

Article(id, topic_id, source_id, title, url, url_hash, author,
        content, content_length, published_at, fetched_at,
        simhash, search_text, status)

Event(id, topic_id, title, summary, first_seen_at, last_seen_at,
      article_count, source_count, status)

ArticleEvent(article_id, event_id, similarity)

FetchLog(id, source_id, started_at, finished_at, new_count, dup_count, error)
```

**关键字段说明**

| 字段 | 用途 |
| --- | --- |
| `url_hash` | 幂等键，防重复入库 |
| `simhash` | 文章级去重指纹（64 位整数） |
| `search_text` | jieba 预分词结果，供 FTS5 索引 |
| `similarity` | 文章与事件中心的相似度，详情页展示 |
| `source_count` | 事件涉及来源数，时间线卡片上的"3 家媒体报道" |

**本地状态（不入库）**

```
localStorage:
  starred_events: [event_id, ...]
  read_events:    [event_id, ...]
  admin_token:    string
```

## 9. 非功能需求

| 类别 | 要求 | 说明 |
| --- | --- | --- |
| 首屏性能 | LCP < 1.5s（4G） | 首页接口只返回事件摘要字段，不返回正文 |
| 抓取性能 | 50 源全量 < 5 分钟 | 并发抓取，单源超时 10s |
| 成本 | LLM ≤ 5 元/天 | 只对事件摘要调用；同事件不重复摘要 |
| 可用性 | 数据库异常时首页可降级 | 返回最近一次快照，页面提示"数据可能不是最新" |
| 安全 | 管理接口凭 Token；全站限流 60 次/分钟/IP | 无用户数据，无个人信息 |
| 合规 | 只抓取公开发布的 RSS；展示保留原文链接与来源名 | 不存储全文图片，不做二次分发 |
| 部署 | 单机部署，SQLite 单文件 | 数据备份 = 复制文件 |
| 适配 | 桌面浏览器 ≥1280px | 只做桌面端，不做响应式；窄屏横向滚动，不降级 |
| 可观测 | 抓取日志 + 处理统计页 | 至少能看到每个源的成功失败情况 |

## 10. 成功指标

### 10.1 产品指标

| 指标 | 目标 | 统计方式 |
| --- | --- | --- |
| 每次打开后点击事件数 | ≥ 3 | 前端埋点（本地计数） |
| 收藏率 | ≥ 10% 的事件被收藏 | 本地计数汇总 |
| 事件平均来源数 | ≥ 2.5 | 数据库统计 |

### 10.2 算法指标（论文用）

| 指标 | 定义 |
| --- | --- |
| 去重精确率 / 召回率 / F1 | 人工标注 100 对，判定"是否重复" |
| 聚类成对精确率 / 召回率 / F1 | 人工标注 50 组，判定"是否同一事件" |
| 摘要忠实度 | 人工三档评分：无新增事实 / 轻微偏移 / 明显错误 |
| 端到端耗时 | 抓取 → 入库的总秒数 |

### 10.3 工程指标

| 指标 | 目标 |
| --- | --- |
| 抓取成功率 | ≥ 95% |
| 文章抽取成功率 | ≥ 90% |
| 首页 P95 响应时间 | < 500ms |

## 12. 风险与应对

| 编号 | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| R01 | X / Reddit 抓取受限（无免费 API、反爬） | 数据源缺失 | 优先用 RSS 与公开 JSON 接口；X 标为 P2，不承诺 |

| R03 | 多领域稀释合并准确率 | 效果 | 每个主题独立阈值；MVP 只开 2 个主题 |
| R04 | 中文全文检索无分词 | 搜索不可用 | jieba 预分词写入 `search_text` |
| R05 | 答辩现场网络不稳定 | 演示失败 | 离线快照模式，一行开关切换 |
| R06 | RSS 源失效 | 数据停滞 | 自动标记失败源、页面提示；保留 3 个以上可用源 |
| R07 | 摘要生成慢影响体验 | 体验 | 摘要异步生成，先展示标题，几秒后补摘要 |
